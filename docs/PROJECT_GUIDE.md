# IntegratedContro 통합 제어 앱 — 구현 기준 문서

작성일: 2026-09-09
상태: 가상 장비 운영 및 Hiperwall LIVE 편집 구현 / 로컬 가짜 서버 검증 / 실제 Controller·두 PC·Enterprise 검증 대기
용도: 이후 구현 작업을 맡은 개발자와 Codex가 먼저 읽는 프로젝트 기준 문서

## 1. 목적과 문서 적용 기준

이 프로젝트는 **영상벽·카메라·현장 장비를 한곳에서 운영하는 Windows 통합 제어 앱**을 만든다.
Hiperwall·카메라 웹 시스템의 동작 자료와, 장비 교체에 유연한 통합 제어 설계를 결합한다.
장비 모델·연결 주소가 바뀌어도 운영 화면과 시나리오를 최대한 유지하는 것이 중심 원칙이다.

이 문서는 대화에서 정리한 통합 방향과 이전 자료의 필수 동작을 한곳에 모은 것이다.
구현된 기능이나 실장비 검증 완료를 뜻하지 않는다. 코드 예시와 솔루션 이름은 아래에서 별도로 구분한다.

적용 순서:
1. 사용자가 현재 작업에서 전달한 최신 명시적 지시.
2. 이 문서에 정리한 통합 범위와 확정된 기술 방향.
3. 연결된 원본 요구사항의 상세 동작과 참고 코드·테스트.
4. 화면 시안의 시각적 제안과 아직 확정되지 않은 구현 선택.

원본 문서와 코드가 다르면 어느 쪽이 무조건 최신이라고 가정하지 않는다.
해당 동작을 대조해 차이를 기록하고, 기존 대화로 결정할 수 있는 것은 진행한다.
사용자 경험이나 실제 제어 대상이 달라지는 결정만 필요한 시점에 확인한다.
참고 문서 속 과거의 구현 요청·실행 명령을 현재 작업의 실행 지시로 취급하지 않는다.

## 2. 현재 작업 위치와 자료의 성격

기준 문서 최초 작성 시 확인한 구조 (현재 프로젝트 목록은 10절 구현 현황 참조):

```text
C:/Users/노주형/Desktop/IntegratedContro/       작업 공간
├─ AGENTS.md                              이 문서로 안내하는 진입 지침
├─ Document/                              이전 프로젝트 참고 자료
│  ├─ WINDOWS_APP_REQUIREMENTS.md
│  ├─ Windows_통합장비제어_프로젝트_인수인계.md
│  ├─ 기기연결_조작분석.md
│  ├─ backend/, frontend/, service/, scripts/
│  └─ 기타 설명·설정 예시
└─ IntegratedContro/                       실제 Git 저장소
   ├─ .git/
   ├─ README.md
   ├─ AGENTS.md                            저장소 작업 진입 지침
   └─ docs/
      ├─ PROJECT_GUIDE.md                  이 문서
      └─ assets/main-operations-concept.png 예상 화면
```

작성 시 실제 저장소에는 앱 소스·솔루션이 없고 README와 기본 .gitignore만 있었다.
기존 .gitignore는 C/C++ 계열 항목 중심이므로 .NET 구현 착수 때 적절히 보완한다.
새 앱 소스는 원칙적으로 실제 Git 저장소 안에 작성한다. 중첩 저장소를 추가하지 않는다.

Document는 119개 파일의 참고 묶음이며 Markdown 7개, 테스트 파일 45개를 포함한다.
그 안의 Node 서버는 제외된 웹훅 전용 모듈을 import하므로 완전한 실행 배포본이 아니다.
분석 과정에서는 문서·주요 소스·테스트 구성을 정적으로 읽었으며 서버·테스트·장치를 실행하지 않았다.
원본 파일은 이식 근거로 보존한다. 이번 기준 문서 작성으로 원본을 수정하지 않는다.

별도 clone에서는 형제 폴더 Document가 없을 수 있다.
이 문서는 핵심 설계와 범위를 독립적으로 이해할 수 있도록 작성했지만,
프로토콜 상세 구현은 필요한 원본 또는 공식 명세를 확보해 대조한다.

### 유지할 기술 방향

- C# + WPF + XAML, MVVM, Windows x64 데스크톱 앱.
- 초기 공식 지원 대상은 Windows 11 25H2 Pro·Enterprise / x64로 확정한다. .NET 10을 사용하며 개발 PC에서 SDK 10.0.400 설치를 확인했다. 솔루션 생성 시 사용할 SDK를 고정하고 패키지 버전은 해당 구현에서 결정한다.
- OS 의존 코드를 분리하여 다른 Windows 버전을 단계적으로 추가한다. 현재 지원 범위 확정은 해당 환경의 앱 검증 완료를 뜻하지 않는다.
- Core/Application은 WPF 컨트롤에 의존하지 않는다.
- 프로필·현장 설정·매핑·작업의 기준 저장소는 SQLite로 통합한다.
- 앱 내부 호출은 ViewModel → 형식화된 C# Application Service로 처리한다. 여러 PC 간 인증·사용권·명령 접수는 공통 실행 호스트의 서비스 계약을 통한다.
- 공통 실행 호스트는 초기에는 운영자 UI와 별도 EXE로 실행하며, 나중에 Windows 서비스로 전환할 수 있도록 실행 수명과 업무 로직을 분리한다. 호스트 데이터는 최초 설정에서 지정한 로컬 폴더에 저장한다. 실제 호스트 PC·폴더 경로·Windows 실행 계정은 현장 설정에서 결정한다.
- Hiperwall·MediaMTX·원격 DeviceAgent 통신은 각각의 클라이언트로 분리한다.
- 영상은 MediaMTX HLS와 검증된 네이티브 영상 엔진을 연결하고 IVideoPlayer 뒤에 격리한다.
- Win32·DDC/CI·Core Audio를 C#으로 캡슐화한다.
- 일반 실행 구조에 Electron·WebView2 화면·Node 백엔드·PowerShell 장치 helper를 포함하지 않는다.
- Windows x64 self-contained 배포를 기본 설계로 하며 설치 형식과 외부 영상 구성요소는 별도 확정한다.

### 초기 Windows 지원 범위와 확장 원칙

초기 공식 지원 대상은 Windows 11 25H2 Pro·Enterprise / x64다.
운영 화면 PC, 공통 실행 호스트 PC, DeviceAgent PC에 같은 초기 범위를 적용하되 구성요소별 동작과 실제 장치를 각각 검증한다.
지원 목록은 설치·실행·업데이트·복구를 확인하고 문제를 수정할 제품 범위이며, 그 밖의 OS에서 반드시 실행 불가능하다는 뜻이 아니다.

- Windows 10, 다른 Windows 11 버전/에디션, Windows Server, ARM64·32비트는 초기 공식 지원에 포함하지 않는다. 실제 현장 요구가 생기면 필요한 조합을 검토하고 검증 후 추가한다.
- 25H2의 특정 누적 업데이트 빌드 하나를 영구 고정하지 않는다. 해당 버전의 보안 업데이트를 반영하며 검증한 에디션·OS 빌드·드라이버·영상 엔진 버전을 기록한다.
- OS 제품/버전/에디션/아키텍처의 공식 지원 판정과 실제 기능 사용 가능 여부를 분리한다. 지원 목록 밖이라는 이유와 필수 기능 부재를 같은 오류로 취급하지 않는다.
- 새로운 Windows 버전은 대표 시나리오·계정/사용권·작업 보존/취소·장비/영상·설치/복구 검증 후 지원 목록에 추가한다. 미래 버전의 호환을 미리 보장하지 않는다.
- 지원 목록·설치 조건·시작 시 진단은 하나의 호환성 정책을 기준으로 관리한다. ViewModel이나 장비별 업무 로직 곳곳에 25H2 문자열 또는 특정 빌드 비교를 넣지 않는다.
- OS 지원 수명과 런타임·외부 라이브러리의 지원 범위는 배포 시점에 다시 확인한다. .NET은 10으로 정했으며 네이티브 영상 엔진은 별도 검증·선정한다.

### 현재 제외하는 범위

- Verkada 웹훅, 서명 검증, 이벤트 모니터링·SSE, 관심 인물 자동 표시.
- 웹훅 대체 폴링, AI 분석, 녹화·재생 시스템.
- 기존 Delphi EXE의 역컴파일 코드 직접 이식 및 특정 MCU 호환 강제.
- 모든 제조사 프로토콜의 일괄 구현, 플러그인 마켓, 동적 DLL 드라이버 로딩.
- 여러 앱에서 한 운영자만 제어하는 사용권 조정은 포함한다. 여러 운영자의 동시 쓰기 제어와 다중 Hiperwall 프로필 동시 운영은 초기 범위에서 제외한다.

일반 장비 제어 인수인계의 “스트리밍 제외”는 그 문서의 개별 범위였다.
통합안에서는 카메라 영상 기능을 별도 모듈로 포함한다.
장비 교체 설계의 “언어 미정”은 통합안의 C# WPF 방향으로 정리한다.
기존 COM1·9600·채널 수·14개 패널 등을 새 시스템의 고정값으로 채택하지 않는다.
Hiperwall은 구체적인 연동 대상이지만 해당 API가 일반 장비 모델 전체를 지배하지 않게 한다.

## 4. 예상 운영 화면과 사용 흐름

![메인 운영 화면 예상 시안](assets/main-operations-concept.png)

이 이미지는 대화에서 ImageGen으로 만든 예상 화면이다.
앱이 실행된 화면이 아니며 장비 수·구역 이름·시간·상태·영상·수치는 모두 예시다.
사진, 대시보드, 평면도는 실제 현장 자산으로 간주하지 않는다.
색상·간격·화면 밀도는 시각적 제안이고, 원본 이미지를 픽셀 단위로 복제하는 것이 목표는 아니다.

| 화면 부분 | 역할 |
|---|---|
| 왼쪽 탐색 | 운영 현황, 영상벽 편집, 카메라, 장비 제어, 시나리오, 연결 설정, 진단·로그 |
| 상단 | 현재 현장·구역, 연결 요약, 시뮬레이션/실장비 구분 |
| 운영자 사용권 | 조회/사용 중/종료 처리/복구 필요, 앱 계정·PC·세션·사용 시작 시각, 사용 시작·사용 종료 |
| 이전 사용자 작업 | 남은 작업 수, 원 요청자·대상·진행 단계·대기/실행/불확실 상태·취소 가능 여부, 상세 보기·선택 취소 |
| 중앙 | 현재 영상벽 배치와 선택 콘텐츠, 별도 카메라 실시간 영상 |
| 오른쪽 | 구역의 조명·프로젝터·승강·음향·매트릭스와 운영 PC 제어 |
| 시나리오 영역 | 운영 시작·종료 등 현장에 정의된 절차 실행 |
| 하단 | 최근 명령의 시각·대상·동작·결과, 필요한 상세 진단 진입 |

운영 현황은 요약과 빠른 조작을 제공하고 세부 편집은 전용 화면으로 연결한다.
빠른 조작과 상세 화면은 같은 Application Service와 상태 저장소를 사용한다.
프로젝터 입력이나 조명 밝기 등은 실제 드라이버가 지원할 때만 표시·활성화한다.

반드시 구분할 사용자 동작:
- 배치 저장 / 현재 인스턴스 변경 / 저장된 배치 표시 / 임시 테스트.
- RTSP 카메라 실시간 영상 / Controller가 주기적으로 제공하는 이미지 프리뷰.
- Hiperwall 콘텐츠 소리 / Hiperwall 전체 음소거 / 현장 음향 / Windows PC 소리.
- 시나리오 실행 취소 / 승강장치의 실제 STOP 명령.
- 연결 성공 / 쓰기 권한 / 장비 응답 / 실제 관측 상태.

시나리오 예시:
“상황실 운영 시작 → 조명 켜기 → 프로젝터 켜기 → 준비 확인 또는 지정 대기
→ 입력 선택 → 음향 설정 → 저장 영상벽 배치 표시”.
예시 순서를 모든 현장에 고정하지 않고 설정으로 구성한다.

## 5. 구조 설계안

아래 구성은 전체 통합 설계안이다. 현재 구현된 프로젝트는 10절의 첫 구현 현황을 따른다.
프로젝트 이름은 IntegratedContro로 통일하는 것을 기본안으로 한다.

```text
IntegratedContro.sln
src/
  IntegratedContro.App/               WPF 화면·ViewModel·전용 컨트롤·시작/종료
  IntegratedContro.Core/              역할·장비·명령·상태·좌표·검증 계약
  IntegratedContro.Application/       운영 서비스·시나리오·표시/종료 Worker
  IntegratedContro.Infrastructure/    SQLite·보호 저장·로그·HTTP/TCP/Serial·영상
  IntegratedContro.Drivers/           가상 장비와 모델별 드라이버
  IntegratedContro.WindowsDevices/    Win32·DDC/CI·Core Audio
  IntegratedContro.DeviceHost/        중단 불가능한 장치 호출의 프로세스 격리
  IntegratedContro.DeviceAgent/       지정 원격 PC의 인증된 장치 제어
tests/
  IntegratedContro.Core.Tests/
  IntegratedContro.IntegrationTests/
  IntegratedContro.UiTests/
docs/
  PROJECT_GUIDE.md
  assets/
```

불필요한 빈 프로젝트를 전부 먼저 만들 필요는 없다. 단계별로 필요한 구현을 추가한다.
Hiperwall·MediaMTX·Semantic 클라이언트는 Infrastructure의 기능별 모듈로 시작할 수 있다.
공통 장비 계약과 전문 영상벽 편집 인터페이스를 구분한다.
여러 PC 운영을 위해 공통 실행 호스트를 UI와 분리한다. 프로젝트 이름은 IntegratedContro.ControlHost를 설계안으로 둔다.
이 호스트는 계정·사용권·작업 저장·명령 실행·Worker의 단일 책임 주체이며, 네이티브 호출 격리용 DeviceHost 및 원격 PC 장치용 DeviceAgent와 역할이 다르다.
WPF 클라이언트는 서비스 계약으로 접속하고 장비 쓰기 경로를 우회하지 않는다. 중앙 상태 변경은 같은 조정 경계에서 처리한다.

### 책임 분리

- UI: 운영 역할·지원 기능·현재 상태·조작 결과 표시.
- Application: 역할 대상 해석, 입력 검증, 작업 순서·복구, 시나리오.
- Driver: 장비 능력 선언, 모델별 명령 변환·응답 해석·제약.
- Transport: 연결 수명·바이트 송수신 또는 HTTP 요청·시간 제한.
- 설정: 구역·연결·장비·역할·화면 노출·시나리오 구성.

Serial/TCP 스트림과 HTTP 요청·응답을 하나의 저수준 API에 억지로 맞추지 않는다.
초기 드라이버 등록은 명시적 레지스트리로 충분하다.

### OS 의존 코드 분리 — 구현 기준

공통 기능의 변경 없이 OS 어댑터와 지원 정책을 추가할 수 있도록 아래 경계를 유지한다.
아래 인터페이스 이름은 구현 시 사용할 계약 예시이며 현재 코드가 존재한다는 뜻이 아니다. 필요한 기능부터 만들고 빈 프로젝트나 범용 플러그인 체계를 먼저 늘리지 않는다.

| 영역 | 공통 계층에 둘 내용 | OS 의존 구현 위치 |
|---|---|---|
| 계정·사용권·명령·시나리오 | 업무 규칙, snapshot, 작업 상태·인계·취소 계약 | Core/Application에는 WPF·Win32·COM·레지스트리 직접 호출을 두지 않음 |
| 화면·입력 | UI 비의존 좌표/검증·작업 결과 모델 | App의 WPF 컨트롤·Dispatcher·DPI/창 이벤트 어댑터 |
| 모니터·오디오·장치 식별 | 지원 기능·명령·관측 결과 계약 | WindowsDevices의 Win32·DDC/CI·Core Audio, 네이티브 호출 격리는 DeviceHost |
| 보호 저장·운영 환경 | ICredentialStore, IPlatformCapabilities 등 필요한 추상 계약 | Infrastructure의 Windows 보호 저장·OS 기능 조회·환경 경로 어댑터 |
| 영상 | IVideoPlayer와 재생 상태/오류 계약 | 네이티브 영상 어댑터에 엔진·코덱·GPU·핸들/자원 해제 의존 격리, WPF 표시 표면은 App에 한정 |
| 시작·설치·업데이트 | 호스트의 작업 수명과 저장/복구 규칙 | 프로세스 진입점·설치 모듈의 Windows 서비스/자동 시작/설치 조건 처리 |

- 의존 방향은 App/ControlHost 등 진입점 → Application → Core로 유지한다. OS 어댑터는 공통 계약을 구현하며 Core/Application이 구체적인 Windows 구현을 참조하지 않는다.
- 네이티브 핸들·COM 객체·WPF 타입은 공통 서비스 계약 밖으로 노출하지 않는다. 장비 ID·기능·관측 상태·결과 등 형식화된 값으로 전달한다.
- 어댑터 선택과 기능 탐지는 각 프로세스의 구성 지점에 모은다. OS 버전만으로 기능 지원을 단정하지 않고 실제 장치·API·영상 엔진의 사용 가능 여부를 확인한다.
- 미지원 기능은 이유와 함께 결과로 반환하고 UI가 해당 조작을 제한한다. 미지원·초기화 실패를 성공이나 다른 PC/장비로의 대체 실행으로 처리하지 않는다.
- 공통 로직은 가상 장비와 가짜 어댑터로 검증하고, OS 어댑터는 지원 OS/실장치 통합 검증으로 구분한다. 처음부터 여러 OS용 별도 업무 로직을 복제하지 않는다.
- OS 확장 시 우선 호환성 정책과 어댑터를 변경한다. 공통 계약 변경이 필요하면 이유와 기존 시나리오·저장 데이터·호스트 통신에 미치는 영향을 명시한다. 추가 지원이 항상 무수정이라는 보장은 하지 않는다.

## 6. 공통 장비 모델과 실행 규칙

### 식별·지원 기능·상태

역할 ID, 장비 ID, 연결 ID를 분리한다.
화면과 시나리오는 가능한 한 역할 ID를 사용한다.

```text
control_room.projector
  → projector_01
  → 해당 모델의 Driver
  → serial_01 또는 network_01
  → 모델별 주소·채널·옵션
```

드라이버는 전원·밝기·입력·음량·뮤트·승강·매트릭스 경로 등의 지원 여부,
값 범위·단위, 조회 가능 여부, 예열/냉각·전송 간격·재시도 제약을 선언한다.
dB·단계·백분율을 혼용하지 않는다. 화면 비율 변환이 필요하면 규칙을 명시한다.
장비 교체 시 역할이 요구하는 기능을 만족하는지 검사한다.

최소 상태:
- DesiredState: 사용자가 요청한 목표값.
- ObservedState: 장비가 보고한 값·관측 시각·신선도.
- LastResult: 최근 명령 결과·확인 수준.
- ConnectionState: 미연결·연결 중·연결됨·복구 대기·오류.

명령 결과는 성공·실패·시간 초과·취소·미지원과 확인 수준을 함께 표현한다.
확인 수준은 전송 완료 / 프로토콜 ACK / 상태 관측으로 구분한다.
저장값이나 ACK만으로 물리 동작 완료를 표시하지 않는다.

### 명령과 시나리오

- 네트워크·DB·장치 작업은 UI를 막지 않고 시간 제한·취소 경로를 둔다.
- 공유 포트/게이트웨이는 연결 단위로 순서를 보장한다.
- 분할·병합 프레임, 불완전 응답, 연결 끊김을 처리한다.
- 재연결과 동작 재실행을 분리한다. 끊긴 동안의 과거 조작을 무조건 재생하지 않는다.
- 증가·토글·승강 등은 응답 유실만으로 자동 재시도하지 않는다. 드라이버가 재실행 가능성을 판단한다.
- 시간 초과·취소 후 이미 전송한 명령은 실제로 실행되었을 수 있다. 조회 가능하면 다시 대조한다.
- 볼륨 누름 반복은 버튼 해제·포커스 상실·화면 이동·연결 끊김에서 멈춘다.
- 승강 STOP은 취소 토큰과 별개이며 실제 드라이버의 명령으로 처리한다.
- 시나리오는 초기 순차 실행으로 구현하고 단계별 제한시간·중단/계속 정책을 둔다.
- 모든 장비에 대한 자동 롤백을 약속하지 않는다. 복구는 필요한 현장의 명시적 절차로 정의한다.

Hiperwall 표시 Worker의 영속 재시도 정책을 모든 물리 장비 명령에 적용하지 않는다.

### 일반 명령·시나리오 snapshot 적용 범위

snapshot은 실행 의도와 대상을 고정하는 기록이며, 과거 권한이나 장비 상태를 유효하게 유지하는 허가가 아니다.

| 대상 | 고정 시점 | 고정할 내용 |
|---|---|---|
| 일반 장비 수동 명령 | Application Service가 검증 후 실행 요청을 접수할 때 | 요청 ID, 현장·실장비/가상 모드, 사용자·앱 세션·사용권 세대, 역할 ID와 해석된 장비/연결 ID, 드라이버·대상 주소/채널의 설정 버전, 동작·값·단위, 제한시간·재시도 규칙 |
| 시나리오 | 실행 시작 시 모든 단계를 검증한 뒤 첫 명령 전 | 실행 ID, 시나리오 정의 버전, 단계 순서·인자·조건·대기·실패 정책, 모든 단계의 해석된 대상과 설정 버전, 실행 사용자·세션·사용권 세대 |
| 시나리오의 영상벽 표시 단계 | 시나리오 시작 시 | 참조 배치·매핑 버전과 표시 대상 snapshot. 단계 도달 시 최신 배치로 다시 해석하지 않음 |

- 실행에 필요한 참조를 일관된 설정 버전에서 해석한다. 나중 단계의 역할을 실행 도중 새 장비로 재해석하지 않는다.
- 화면 표시 이름 등 실행과 무관한 변경은 기존 실행에 영향을 주지 않는다. 대상·주소·기능 등 관련 설정 버전 변경, 대상 삭제·비활성화, 장치 식별/topology 불일치는 다음 전송을 차단하고 재검토가 필요한 중단으로 기록한다.
- 설정 변경 때문에 중단된 시나리오는 최신 설정으로 새 실행을 시작한다. 기존 snapshot을 덮어쓰거나 일반 단계의 '실패 시 계속' 정책으로 이 검사를 우회하지 않는다.
- 신규 사용자 요청 접수 시 현재 계정 권한과 유효한 사용권 세대를 검사한다. 접수 완료 작업의 전송 시에는 호스트의 실행 소유권, 접수 당시 승인 범위, 현재 계정/대상 권한과 작업 취소·만료·제약을 검사한다. 정상 사용 종료에 따른 세션/사용권 반납만으로 접수 작업을 무효화하지 않는다.
- 취소된 작업의 미전송 명령과 접수되지 않은 이전 세션 요청은 전송하지 않는다. 접수 완료 작업은 아래 보존·취소 정책을 따른다. 계정 비활성화나 제어 권한 회수는 단순 로그아웃과 구분해 영향을 받는 후속 전송을 차단하고 사유를 표시한다.
- 관측 상태·연결 상태·준비 여부는 각 단계에서 최신 상태로 평가한다. 시작 시의 관측값을 이후 조건 충족의 증거로 재사용하지 않는다.
- 비밀값은 snapshot에 복제하지 않고 보호 저장 참조를 사용한다. 자격 증명 교체가 대상·권한을 바꾸면 재검증하며, 오래된 인증 정보를 복원해 실행하지 않는다.
- 실행 의도와 결과는 전송 전후로 기록한다. 사용자 교대 중 호스트의 정상 실행 지속과 호스트 재시작 후 복구를 구분한다. 재시작 시 전송 여부나 결과가 불명확한 일반 장비 명령은 자동 재전송하지 않고 상태 대조 대상으로 남긴다. 작업 보존이 불확실한 명령의 재실행을 허가하지 않는다.
- 슬라이더 등 아직 전송하지 않은 요청을 합치는 경우에도 최신 요청과 대체된 요청을 구분한다. 이미 전송한 요청이나 시작한 시나리오의 snapshot은 수정하지 않는다.

### 수동 조작과 시나리오 충돌 — 확정 정책

사용자가 선택한 세 번째 방식인 '시나리오 대상 예약 + 명시적인 중단 후 수동 전환'을 적용한다.
전환은 현재 사용권자가 시나리오 실행을 중단하고 수동 조작으로 바꾸는 동작이다. 사용 종료는 접수된 시나리오를 유지한 채 사용권을 반납하며, 다음 사용권자는 이전 사용자의 시나리오에도 같은 수동 전환 정책을 적용할 수 있다.

- 시나리오 시작 시 모든 단계가 사용할 장비를 예약한다. 현재 단계가 대기 중이어도 이후 사용할 장비의 충돌 조작은 제한한다.
- 초기 예약 단위는 역할 이름이 아닌 실제 장비 ID로 한다. 서로 다른 역할이 같은 장비를 가리켜도 충돌로 판단하고, 공유 연결의 전송 순서는 별도로 유지한다.
- 예약 대상 수동 조작 시 실행 중인 시나리오와 중단 영향을 표시하고 '시나리오 중단 후 수동 전환'을 제공한다. 전환을 선택하기 전에는 해당 수동 명령을 보내거나 대기열에 넣지 않는다. 전환 안내를 취소하면 수동 명령 없이 기존 시나리오를 계속한다.
- 현재 사용권자가 전환을 선택하면 해당 시나리오 전체의 후속 단계와 미전송 명령을 먼저 차단한다. 단계의 '실패 시 계속' 정책이나 늦게 도착한 응답으로 다음 단계가 실행되지 않도록 한다.
- 이미 전송한 명령의 결과·불확실 상태와 장비 제약을 확인한 뒤 수동 조작 가능 여부를 결정한다. 전환 처리 중에는 충돌하는 새 명령을 차단하며, 확인되지 않은 물리 동작을 완료로 처리하지 않는다.
- 전환 처리가 끝나면 수동 조작을 활성화하고 사용자가 원하는 명령을 다시 선택하도록 한다. 처음 눌렀던 충돌 명령을 뒤늦게 자동 실행하지 않는다. 전송 직전 권한·사용권·대상 유효성을 다시 검사한다.
- 중단한 시나리오는 자동 재개하거나 이미 수행한 동작을 자동 롤백하지 않는다. 정상 완료 또는 중단 정리가 끝나면 예약을 해제하되, 결과가 불확실한 장비는 상태 대조와 장비별 제약을 충족할 때까지 충돌 조작을 제한한다.
- 시나리오가 사용하지 않는 장비의 수동 조작과 조회는 허용한다. 전원·매트릭스 등 다른 대상에도 영향을 미치는 조작은 영향 대상까지 충돌 범위에 포함한다.
- 지원되는 승강 STOP은 현재 사용권자가 일반 수동 전환 확인 없이 예약과 무관하게 요청할 수 있다. 해당 시나리오의 후속 단계·미전송 명령을 차단하고, STOP을 미전송 일반 명령보다 우선 처리한다. 이미 전송 중인 바이트/중단 불가능 호출을 즉시 취소할 수 있다고 가정하지 않으며 STOP 후 시나리오를 자동 재개하지 않는다.
- 조회 중인 다른 운영자의 STOP 허용 여부는 별도 미결정이다. 사용권이 없는 앱에 일반 제어 우회 경로를 만들지 않는다.

예: '운영 시작' 시나리오의 프로젝터 예열 대기 중 전원 끄기를 선택하면 수동 전환 안내를 표시한다.
운영자가 전환하면 남은 자동 단계를 차단하고 전송 결과·예열/냉각 제약을 확인한다.
수동 조작 가능 상태가 된 뒤 운영자가 전원 끄기를 다시 선택할 때 새 명령으로 검증·실행한다.

'실행 종료까지 수동 조작을 일괄 차단'과 '수동 조작만으로 시나리오를 자동 중단'하는 방식은 채택하지 않는다.
'시나리오 중단 후 수동 전환'은 구현 기준이며, 이 문서의 정책 확정이 앱 구현이나 실장비 검증 완료를 뜻하지 않는다.

### 여러 PC·앱 자체 계정·운영자 사용권

확정 요구: 여러 PC에서 앱을 실행하고 앱 자체 계정으로 로그인한다.
권한이 있는 한 사용자의 한 앱 세션만 신규 제어 요청을 할 수 있으며, 현재 사용자의 '사용 종료' 후 다음 사용자가 '사용 시작'으로 사용권을 얻는다.
사용 종료는 접수된 작업의 취소가 아니다. 이미 접수된 작업은 원 요청자 정보와 함께 공통 실행 호스트에 남는다.

- 공통 실행 호스트가 앱 계정·권한·사용권·접수 작업의 기준 정보를 관리한다. Windows 로그인 이름이나 클라이언트가 보낸 사용자 이름만으로 앱 권한을 인정하지 않는다.
- 계정 인증·세션 검증은 호스트에서 수행한다. 비밀번호 원문을 저장·로그·내보내기에 남기지 않고 비밀번호 검증용 해시로 관리한다. 인증 통신 보호·계정 복구·세부 권한표는 구현 시 구체화한다.
- 초기 계정 정책은 '호스트 최초 설정에서 관리자 생성 → 관리자가 운영자 계정 등록'이다. 최초 관리자 생성은 초기 설정 권한을 확인한 설정 경로에서 한 번만 허용하고, 초기화 완료 상태를 영속 저장한다. 단순 재시작이나 계정 문제를 신규 초기화로 간주하지 않는다.
- 이 계정 생성 방식은 초기 정책이며 이후 운영 요구에 따라 변경할 수 있다. 초기 설정·계정 등록 절차를 인증/사용권/명령 실행 규칙과 분리하여 변경 범위를 제한한다. 변경 시 기존 계정 ID·작업 요청자·취소자·감사 이력을 보존하며, 향후 변경 가능성이 현재 앱 자체 계정 요구를 해제하지는 않는다.
- 사용자 권한은 제어 자격, 사용권은 신규 제어를 요청할 앱 세션의 배타적 소유를 뜻한다. 같은 계정의 두 앱도 서로 다른 세션으로 취급한다. 이전 사용자의 접수 작업 실행은 두 번째 사용권 부여가 아니다.
- 기본 제어 범위는 같은 현장의 공유 제어 대상 전체다. 현장/프로필 이름만 달리해 같은 물리 장비를 중복 소유하지 않도록 대상 중복을 검사한다. 구역별 동시 제어는 별도 확장이다.
- 사용권이 없는 앱은 허용된 상태 조회와 로컬 초안 편집을 할 수 있다. 신규 장비 명령·시나리오 시작·LIVE 변경·공유 설정 반영·원격 발행·작업 취소는 사용권과 해당 권한을 함께 요구한다. 관리자 복구 인계는 별도 관리 권한으로 처리한다.
- 사용 시작 경쟁과 명령 접수는 공통 호스트에서 원자적으로 처리한다. 사용자 ID·PC/앱 세션 ID·사용권 세대를 검증하며, PC별 플래그나 각 PC의 로컬 SQLite로 소유를 판정하지 않는다.
- 사용 종료는 해당 세션의 신규 접수 차단 → 접수 완료/미접수 경계와 남은 작업 목록 확정 → 사용권 반납 순서다. 진행 중 작업의 완료를 기다리거나 일괄 취소하지 않는다. 반납 전까지 다른 세션에 사용권을 부여하지 않는다.
- 세대가 바뀐 뒤 도착한 이전 세션의 미접수 요청은 거부한다. 이미 접수된 요청 ID의 재조회/재시도는 기존 작업을 반환하며 중복 작업을 만들지 않는다. 실제 장비 쓰기는 호스트가 관리하는 실행 경로만 사용한다.
- 사용 종료로 장비 전원을 끄거나 영상벽을 닫지 않는다. 원 요청자·snapshot·작업 ID를 유지하고 다음 사용자의 요청으로 바꾸지 않는다. 완료/취소된 시나리오를 교대 때문에 재개하지 않는다.
- 이 사용권은 본 앱의 명령 경로를 조정한다. 제조사 앱·물리 리모컨의 외부 조작까지 차단한 것으로 표시하지 않으며 관측 결과에 반영한다.

### 사용 종료 후 접수 작업 보존·표시·취소

- 접수 완료는 호스트가 권한·사용권·대상을 검증하고 요청 ID, snapshot, 실행 상태를 영속 저장한 상태다. 클라이언트 화면의 초안·버튼 입력·로컬 대기열은 포함하지 않는다.
- 보존 대상은 접수된 일반 명령, 시나리오와 그 안에 고정된 미실행 단계, 표시 작업 및 예정된 종료/정리 작업이다. 사용자가 없어도 공통 호스트가 기존 일정·조건·제약에 따라 정상 실행을 이어간다. 반복 누름 입력이 끝나는 규칙이나 요청 자체의 만료를 연장하지 않는다.
- 모든 접속 앱에 '이전 사용자 작업 N건'을 별도 표시한다. 다음 사용권자는 원 요청자, 요청 시각, 대상, 작업 종류, 현재 단계, 남은 단계/종료 예정, 최신 결과·불확실 상태, 취소 가능 범위를 확인할 수 있어야 한다. 같은 계정의 이전 세션 작업도 구분한다.
- 다음 사용권자는 자신의 제어 권한 범위 안에서 이전 사용자의 남은 작업을 선택 취소할 수 있다. 일반적인 작업 취소에 관리자 권한이나 원 요청자의 재접속을 요구하지 않는다. 조회 세션은 취소할 수 없다.
- 취소와 전송은 호스트에서 순서를 판정한다. 아직 전송하지 않은 명령과 시나리오 후속 단계는 취소하고, 이미 전송한 명령은 결과 대조 대상으로 남긴다. '취소 요청', '미실행 부분 취소 완료', '이미 전송됨/결과 확인 필요'를 구분한다.
- 취소는 이미 발생한 물리 동작을 되돌리거나 STOP을 보냈다는 뜻이 아니다. 장비별 STOP 또는 열린 표시의 종료가 필요하면 지원되는 별도 동작으로 명확히 처리한다. 표시 종료 작업을 취소해 자동 종료가 사라지는 경우에는 그 결과를 조작 화면에 표시하며, 미종료 인스턴스 추적 기록은 유지한다.
- 이전 시나리오의 장비 예약과 공유 연결 순서는 교대 후에도 유지한다. 새 사용자가 충돌 장비를 조작하려면 확정된 '시나리오 중단 후 수동 전환'을 적용한다. 관련 없는 장비 조작은 허용한다.
- 단순 교대가 아닌 계정 권한 회수·작업 만료·설정 불일치·호스트 장애 시에는 관련 전송을 차단하거나 대조 대기로 전환한다. 보존만을 이유로 불확실한 명령을 자동 재전송하지 않는다.
- 원 요청자와 별도로 취소 요청자·취소 시각·취소 결과·인계 이력을 기록한다. 활성/미완료 작업과 불확실 결과를 보존 정책으로 삭제하지 않는다.

### 연결 이상 시 관리자 복구 인계

확정 순서: 연결 이상 표시 → 이전 세션의 명령 차단 확인 → 진행 중 작업 확인 → 관리자가 복구 인계.

- 앱 비정상 종료나 연결 단절을 감지하면 '연결 이상/복구 필요'와 마지막 확인 시각을 표시한다. 시간 경과만으로 다른 앱에 사용권을 자동 부여하지 않는다.
- 호스트는 이전 세션의 신규 접수 경로를 차단하고 이전 세대의 늦은 요청을 거부하는 상태를 확인한다. 이 차단은 이미 접수된 정상 작업의 일괄 취소를 뜻하지 않는다.
- 관리자는 접수 완료 목록, 미접수/접수 여부 확인 대상, 진행 중 전송, 남은 시나리오·예약과 불확실 결과를 확인한다. 호스트가 정상인 작업은 기존 실행을 유지한다.
- 이전 세션 차단과 진행 상태 확인을 마친 뒤 관리자가 복구 인계를 승인하고 이전 사용권을 정리한다. 다음 운영자는 '사용 시작'으로 사용권을 얻어 남은 작업을 검토·취소할 수 있다. 관리자의 복구 인계가 모든 작업의 성공·물리 완료를 뜻하지 않는다.
- 차단을 확인할 수 없거나 호스트에 연결할 수 없으면 새 사용권을 발급하지 않는다. 불확실한 개별 장비는 충돌 조작 제한을 유지하며, 호스트 재시작은 작업 기록과 장비 상태를 대조한다. 호스트 다중화·자동 장애 전환은 초기 범위에 포함하지 않는다.
- 생존 확인 주기·판정 시간·호스트 설치 위치는 추후 결정한다. 복구 승인 주체가 관리자라는 점과 위 인계 순서는 확정이다.

### 시뮬레이션과 실제 제어

가상 장비도 실제 드라이버와 같은 계약을 사용한다.
초기 가상 대상은 조명·프로젝터·음향·승강이며 매트릭스는 해당 단계에서 추가한다.
동일 역할에 기능 구성이 다른 두 가상 모델을 배정하여 교체 유연성을 확인한다.
정상·지연·무응답·실패·끊김·재연결·전송 후 응답 유실을 주입할 수 있게 한다.
가상 상태를 실제 장비 연결·실측으로 표현하지 않는다.

기존 DRY_RUN은 Hiperwall 쓰기 차단이며 모니터·사운드 전체를 막는 기능이 아니다.
새 UI에서도 적용 범위를 표시한다. 통합 시뮬레이션과 Hiperwall DRY_RUN은 별개다.
가상 모드에서 실제 드라이버를 자동 호출하는 fallback을 만들지 않는다.

## 7. 영상벽·저장 배치의 필수 동작

- Controller 제품·버전·인증·역할·권한을 구분한다. 읽기 가능이 쓰기 권한을 뜻하지 않는다.
- Contents 폴더는 표시상 분리하되 저장·전송에는 원문 전체 이름을 보존한다.
- Source는 UUID를 우선 사용하고 UUID 없는 콘텐츠는 전체 이름으로 식별한다.
- 자유 Wall 편집은 추가·이동·크기·팬·줌·비율·스냅·소리·닫기를 제공한다.
- 신규 자유 배치는 원본 크기로 열고 Zone보다 크다는 이유로 자동 축소하지 않는다.
- Zone 버튼으로 이동할 때 크기를 보존하며 해당 Zone 중앙으로 옮긴다.
- 자유 Wall 편집의 Zone 경계 밖 이동을 허용한다. 저장용 Zone 편집의 제약과 혼동하지 않는다.
- 인스턴스별 변경은 순서대로 보내고 대기 중인 오래된 변경은 최신 값으로 합친다.
- 전체 닫기는 사용자 확인과 인스턴스 집합 revision 검증 후 해당 snapshot만 개별 종료한다.
- 전체 닫기의 성공·실패·남은 수를 표시한다. 종료 정리는 해당 실행 주체가 정리할 책임을 가진 앱 소유 인스턴스만 대상으로 하며, 사용권 교대 자체는 표시 종료 사유가 아니다.

### 좌표 계약

- 저장 모델은 Hiperwall 배치 공간의 절대 중심 X/Y, Y는 아래쪽으로 증가한다.
- open/change XML 생성 시에만 Y를 반전한다: hiperwallY = -appY.
- 예: 중심 (100, 200), 크기 (640, 360) → x=100, y=-200, boundsw=640, boundsh=360.
- Zone은 left/top/width/height이며 중심 좌표와 구분한다.
- 음수·소수를 허용하고 크기는 유한한 양수로 검증한다.
- 구형 percent 배치는 좌상단 백분율이다. pixels 중심 좌표로 명시적으로 변환한다.
- WPF DIP·화면 픽셀·Wall 좌표를 구분하고 DPI·팬·줌으로 저장값이 달라지지 않게 한다.
- UI 비의존 LayoutGeometry에 변환·히트 테스트·비율·스냅을 모은다.

### 저장·표시·복구

배치 저장은 SQLite 트랜잭션으로 처리하며 현재 화면에는 명령을 보내지 않는다.
수동 표시는 저장된 매핑을 읽어 일반 표시 요청과 target snapshot을 먼저 영속화한다.
가짜 Verkada 이벤트를 만들어 기존 이벤트 경로에 넣는 방식은 사용하지 않는다.
이미 생성된 작업의 snapshot은 나중의 매핑 수정으로 바꾸지 않는다.

임시 테스트는 미저장 초안으로 실행하고 기본 15초 뒤 닫는다.
open 전에 종료 예정 시각을 기록하고 재시작 후 Controller 목록과 대조한다.
메모리 타이머만으로 자동 종료를 구현하지 않는다.
자유 Wall의 다중 인스턴스를 카메라당 단일 표시 정책으로 제한하지 않는다.
자유 open의 영속 복구는 기존 구현에 완비된 기능이 아니므로 별도 설계·검증한다.

표시 시간은 앱 모델에서 Default / Timed / Continuous를 구분하는 것을 설계안으로 한다.
Timed는 1~86,400초 정수, Continuous는 자동 종료 없음이다.
기존 파일의 누락 값은 기본 시간, null은 계속 표시로 명시적으로 이관한다.
원본 요구사항은 계속 표시를 후속 기능처럼 설명하지만 README·소스·테스트에는 이미 존재한다.
이 통합안에서는 계속 표시를 보존한다.

Hiperwall 응답은 HTTP 2xx라도 XML Error가 있으면 실패다.
close 404는 실제 목록에서 인스턴스가 없음을 확인해야 종료 성공으로 볼 수 있다.
기존 Worker의 참고 기본값은 poll 1초, lease 60초, 최대 8회, backoff 5~300초다.
408/429/5xx·전송 장애와 잘못된 요청·권한·오래된 매핑을 구분한다.

## 8. 카메라·프리뷰·Semantic

### 카메라와 영상

- 일반 RTSP 카메라 등록과 Hiperwall Source 매핑을 분리한다.
- 카메라 등록만으로 Hiperwall Source가 자동 생성된다고 가정하지 않는다.
- 1차 영상 경로는 RTSP → MediaMTX → HLS → 네이티브 WPF 영상 어댑터다.
- 엔진 선정 전에 실제 코덱·지연·재연결·음소거·자원 해제·x64 배포 조건을 검증한다.
- 엔진 미선정 상태에서는 인터페이스와 가상 플레이어로 독립 작업을 진행할 수 있다.
- 등록 정보 저장과 MediaMTX 경로 준비의 성공/실패를 구분한다.
- 일반 삭제 실패 시 등록을 유지한다. 명시적 강제 삭제는 정확한 경로를 정리 큐에 남긴다.
- 시작 시 재동기화하며 경로 삭제 큐는 기존 30초 주기를 참고한다.
- RTSP 계정은 보호 저장하고 UI 조회·로그·일반 내보내기에 원문을 노출하지 않는다.
- MediaMTX는 독립 자격 증명을 사용한다. Docker/별도 프로세스 배포는 설치 환경에 맞춰 결정한다.

### Wall 이미지 프리뷰

Controller의 JPEG/PNG를 주기적으로 받아 편집 사각형에 표시한다.
보이는 콘텐츠만 요청하고 같은 콘텐츠의 인스턴스들은 결과를 공유한다.
참고 기본값: 일반 콘텐츠 3초, 이미지 콘텐츠 60초, 동시 요청 2개,
이미지당 4MiB, 캐시 64개/24MiB.
실패해도 편집을 유지하고 이전 이미지에는 갱신 실패 상태를 표시한다.
화면 숨김·최소화·이탈에서 요청과 이미지 자원을 정리한다.
현재 인벤토리의 selector/value만 허용하고 프리뷰를 디스크에 보관하지 않는다.
디코딩 후 메모리 크기도 별도로 제한한다.

### Semantic

로컬 매핑이 기준이며 원격 태그는 로컬을 자동 수정하지 않는다.
유일한 참조 일치·유일한 정규화 이름 일치만 복구/초기 후보로 제시한다.
기존 100%/90% 표시는 규칙 기반 등급이며 측정된 통계 정확도가 아니다.
승인은 기존 Zone·배치·활성화·표시 시간을 보존한다.
배치 없는 후보는 운영자가 Zone 배치를 검토·저장하도록 연결한다.
배치 승인은 최대 500개를 전부 검증한 뒤 원자적으로 반영한다.

명시적으로 선택한 항목만 SQLite outbox에 넣고,
쓰기 직전 소유권 재검사 → 쓰기 → 재조회 검증 순서로 처리한다.
충돌·중복·다른 배포 소유·generation 변경·삭제된 대상 등을 구분한다.
DTD/ENTITY, 응답/객체/JSON 크기·깊이, 허용 필드를 제한한다.
원격 발행 데이터는 schema/producer/deploymentRef/cameraRef/registryRef/generation/updatedAt만 사용한다.
기존 verkada.bridge.v1·verkada-bridge·조직/카메라 ID 의존성은 새 식별 체계로 교체한다.
새 namespace와 producer 값은 구현 시 버전과 함께 결정하며 기존 태그를 자동 덮어쓰지 않는다.

## 9. Windows 장치·저장·앱 수명

### Windows 장치

초기는 한 대의 지정 대상 PC를 기준으로 한다. 여러 PC의 장치를 동시에 선택하는 기능은 후속 범위다.
모니터·오디오 등 PC 장치 제어는 항상 PC ID와 장치 ID로 대상을 확정하고, 화면에 실제 대상 PC 이름을 표시한다.

- PC 이름과 IP/접속 주소는 표시·연결 정보이며 식별 키로 사용하지 않는다. 실제 장비 PC에 등록된 PC ID와 해당 PC 안의 장치 ID를 함께 저장하고 명령 snapshot에도 포함한다.
- 대상 미설정 시 관련 조작을 비활성화한다. '로컬'이라는 이유로 현재 UI PC나 호스트 PC를 자동 선택하지 않는다. 같은 PC의 장치를 제어할 때도 명시적으로 등록·선택한 ID를 사용한다.
- PC 이름 변경·IP 변경·운영자 교대가 제어 대상 변경을 뜻하지 않는다. 인증된 장치 연결에서 PC ID를 확인하고, 장치 ID·topology·출력 장치 변경은 전송 전에 재검증한다. 이름이 같다는 이유로 다른 PC를 기존 대상으로 연결하지 않는다.
- 접속 주소의 PC ID가 다르거나 장치 재등록/교체로 ID가 바뀌면 기존 요청을 거부하고 명시적인 재배정·검토를 요구한다. 새 대상 ID를 기존 snapshot에 덮어쓰지 않는다.
- 조작 화면·작업 상세에는 실제 PC 이름과 장치 이름을 표시한다. 이름 중복 또는 오래된 조회 정보는 구분 표시하고 상세 화면에서 PC ID·장치 ID·마지막 확인 시각을 확인할 수 있게 한다.
- 기본 오디오 출력은 접수 시 실제 출력 장치 ID로 해석하고 전송 시 다시 대조한다. 출력이 바뀌었다고 기존 명령을 새 기본 출력에 자동 적용하지 않는다.
- 원격 연결 실패 시 앱 실행 PC나 호스트 PC의 장치로 대체 실행하지 않는다.

모니터 ID·topology, 오디오 기본 출력 ID를 재검증하여 오래된 대상 요청을 거부한다.
밝기·볼륨은 정수 0~100, 볼륨 변경은 음소거 상태를 보존한다.
물리 모니터 식별이 불명확하면 개별 제어를 차단한다.
전원은 DDC/CI VCP 0xD6의 1/5를 참고하며, 5초 후 조회·실패 시 2초 뒤 한 번 더 조회한다.
조회 실패를 꺼짐으로 표시하지 않는다.

기존 모니터·사운드의 동시 1개·대기열 없음·최대 30초 계약을 유지한다.
중단 불가능한 네이티브 호출은 DeviceHost로 격리하고 시간 초과 시 실제 프로세스를 정리한다.
Task 대기 취소만으로 네이티브 실행이 중단되었다고 처리하지 않는다.
DeviceAgent는 독립 토큰, 허용 명령만 제공하고 로그인 사용자 세션에서 실행한다.
UI 스레드에서 네이티브 작업을 실행하지 않으며 핸들·COM 참조를 해제한다.

### 데이터·자격 증명

주요 저장 대상: 버전별 현장 설정, 연결·장비·역할·구역, 프로필, 카메라,
매핑, 표시 요청·작업·시도 이력·인스턴스, 경로 정리 큐, Semantic 식별/outbox,
시나리오 정의·실행 결과, 일반 명령·시나리오 snapshot, 앱 계정·권한·인증 세션, 운영자 사용권·세대·인계 이력, 원 요청자와 취소 요청자·취소 처리 이력.

SQLite를 기준 저장소로 하고 JSON은 비밀 제외 가져오기·내보내기에 사용한다.
사용권 조정용 공통 저장소와 앱별 초안/캐시를 구분한다. 여러 PC가 각자의 SQLite를 권위 있는 사용권 저장소로 사용하는 구조는 채택하지 않는다.
공통 실행 호스트가 운영 SQLite를 소유하고 클라이언트는 서비스 계약으로 접근한다. 클라이언트 로컬 초안/캐시를 운영 기준 데이터나 접수 완료 작업으로 취급하지 않는다.
기존 SQL은 참고하되 display_jobs.event_id FK, Verkada 조직 필드,
Semantic producer 제약 등을 새 모델에 맞춰 마이그레이션한다.
Windows 보호 저장소의 사용자/장치 범위는 배포 환경에 맞춰 확정한다.
옛 공유 secret에서 파생된 암호화·로그·인증 키를 독립 체계로 교체한다.
기존 암호문은 기존 키로 복호화·재암호화하거나 자격 증명을 다시 입력한다.

클라이언트 화면 설정·초안은 %LOCALAPPDATA%/<앱 이름>/ 아래에 둔다. 호스트의 운영 DB·설정·로그·복구 기록은 지정한 로컬 데이터 폴더에 둔다. 구체적인 경로는 호스트 최초 설정에서 선택하며 설치 폴더·현재 작업 디렉터리·운영자 프로필로 자동 대체하지 않는다. 보호된 자격 증명은 선택한 보호 저장 범위를 따르고 원문을 데이터 폴더에 저장하지 않는다.
로그에는 인증 헤더·토큰·RTSP 원문·Hiperwall 응답 원문/detail을 남기지 않는다.
참고 보존 기준은 운영 로그 14일/100MiB, 완료 DB 기록 30일이다.
활성 작업·미종료 인스턴스·미완료 정리 작업은 만료 청소에서 보존한다.

### 수명

시작: 설정·보호 저장·DB 마이그레이션 → 화면 표시와 외부 상태 조회 → 사용권/공통 실행 책임 확인 → 복구 대조 → 실행 책임이 있는 Worker.
조회용 앱을 추가 실행했다는 이유로 장비 연결·복구·정리 Worker를 중복 시작하지 않는다. DB 마이그레이션도 하나의 실행 주체가 직렬 처리한다.
외부 장애나 설정 미완료가 설정 화면의 실행을 막지 않게 한다.
제어 중인 앱의 종료는 사용 종료 절차와 연계한다. 조회 앱 종료는 다른 사용자의 제어나 공통 Worker를 중지하지 않는다.
실행 호스트 종료: 신규 명령 차단 → Worker 중지 → 정리 대상 소유 인스턴스 처리 → 영상·장치 프로세스·DB 해제.
사용 종료와 작업 취소를 구분한다. UI 정상 종료는 신규 접수와 사용권만 정리하며 접수된 일반 명령·시나리오·표시/정리 작업은 호스트에 유지한다. UI 비정상 종료는 관리자 복구 인계 절차를 따른다.
미완료 복구 정보를 남기고 다음 실행에서 이어 처리한다.
최소화·화면 숨김과 프로세스 종료를 구분한다.
초기 호스트 EXE는 모든 운영자 UI가 닫혀도 실행을 유지하며 접수 작업을 처리한다. 호스트 EXE 종료·Windows 로그아웃·PC 재부팅 이후에는 다시 실행해야 하며, 중단 동안 Worker는 동작하지 않는다. 자동 시작 정책은 추후 결정하고 Windows 서비스 전환은 후속 단계로 둔다.
앱 중복 실행 허용과 배타적 사용권은 구현 요구다. 자동 실행·트레이·설치 업데이트 정책은 배포 단계에서 명시적으로 정한다.

### 공통 호스트 EXE·서비스 전환·지정 로컬 데이터 폴더 — 확정 정책

초기에는 별도 호스트 EXE로 개발하고, 나중에 Windows 서비스로 전환 가능한 구조를 유지한다.
호스트 운영 데이터는 사용자가 지정한 호스트 PC의 로컬 폴더에 저장한다. 특정 드라이브나 경로는 아직 지정되지 않았으며 예시 경로를 실제 설정으로 고정하지 않는다.

- 운영자 WPF 앱과 호스트 EXE는 별도 프로세스로 실행한다. UI 종료가 호스트 종료를 유발하지 않으며, 운영자의 사용 종료는 기존 접수 작업을 취소하지 않는다.
- 계정·사용권·작업 실행·SQLite·복구 로직은 공통 호스팅 계층에 둔다. EXE 실행과 Windows 서비스 실행의 차이는 진입점·시작/종료 어댑터·설치 설정에 한정한다.
- 실행 중인 호스트는 팝업이나 콘솔 입력을 기다리지 않는다. 최초 설정 절차는 정상 명령 처리 수명과 분리하고, 초기화가 필요한 경우 상태와 설정 진입 방법을 제공한다.
- 데이터 루트 경로는 명시적인 시작 설정으로 전달한다. 해당 경로를 찾기 위한 최소 시작 설정에는 운영 DB나 비밀값을 복제하지 않는다. EXE와 향후 서비스가 같은 설정 계약을 사용한다.
- 최초 설정에서 로컬 데이터 폴더의 절대 경로·접근 권한·쓰기 가능 여부를 확인하고 신규 현장 초기화와 기존 데이터 열기를 구분한다. 클라이언트가 SQLite를 네트워크 공유 폴더로 직접 열지 않는다.
- 설정한 데이터 폴더가 없거나 접근 불가능하면 호스트를 설정/진단 상태로 두고 신규 제어와 Worker 실행을 차단한다. 다른 경로에 빈 DB를 자동 생성하여 새 현장이나 새 관리자 초기화로 처리하지 않는다.
- 운영 DB·현장 설정·로그·작업/복구 정보를 지정 폴더 아래에서 관리한다. 자격 증명·암호화 키는 보호 저장 정책을 따르며 폴더 백업만으로 다른 실행 계정/PC의 복호화가 보장된다고 가정하지 않는다.
- 같은 데이터 폴더/DB에 대한 호스트 실행 소유는 하나로 제한한다. 여러 운영자 앱의 중복 실행 허용과 호스트의 중복 실행 방지를 구분한다.
- 폴더 이전은 호스트를 중지해 일관된 데이터와 자격 증명 이전 계획을 확보한 뒤 경로를 변경하고 복구를 검증한다. 실행 중인 DB 파일만 임의로 복사해 전환하지 않는다.
- Windows 서비스 전환 시 기존 EXE를 먼저 중지하고 실행 계정·데이터 폴더·인증서/보호 저장 접근을 확인한다. 동일한 현장 ID·계정 ID·접수 작업·감사 이력을 유지하며, 전송 결과가 불명확한 명령을 자동 재실행하지 않는다.
- 사용자 로그인 세션이 필요한 모니터·오디오는 대상 PC의 DeviceAgent에 유지한다. 서비스 전환을 이유로 호스트 PC의 장치나 서비스 세션으로 대체하지 않는다.
- 서비스 등록·자동 시작·장애 재시작·업데이트 정책은 서비스 전환 단계에서 구체화하고 검증한다. 이번 선택은 서비스 설치나 자동 실행 등록을 요청한 것이 아니다.

앱 자체 계정과 호스트의 Windows 실행 계정은 별개다. Windows 실행 계정과 실제 호스트 PC는 아직 미정이다.
초기 EXE 개발은 현재 개발 계정으로 시작할 수 있으며, 서비스 전환 시에는 필요한 권한만 가진 전용 계정을 권장한다. 계정 변경 시 데이터 경로만 맞추는 것으로 충분하다고 가정하지 않는다.
호스트 PC는 전용 PC이면 운영자 PC 재시작과 분리하기 쉽고, 기존 운영 PC 겸용이면 초기 장비 부담은 낮지만 재부팅·절전·고장이 공통 호스트에도 영향을 준다.

참고: [Windows 서비스 구성](https://learn.microsoft.com/en-us/dotnet/core/extensions/windows-service), [서비스와 사용자 세션 분리](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services), [Windows 보호 저장](https://learn.microsoft.com/en-us/dotnet/standard/security/how-to-use-data-protection).

### Hiperwall Zone 바로가기 (2026-09-14)

- 캔버스 바로 아래에 응답 Zone별 작은 버튼을 표시한다. 선택 Zone과 드롭 대상은 색으로 구분하고,
  같은 이름의 Zone은 ID로 구분한다. 버튼이 많으면 가로 스크롤한다.
- 클릭/탭은 대상 Zone을 선택하고 해당 영역이 보이도록 캔버스를 맞춘다. 소스를 이동시키는 명령은 보내지 않으며 조회 모드에서도 탐색할 수 있다.
- 캔버스의 열린 소스를 마우스/한 손가락으로 버튼에 놓으면 해당 Zone 중앙으로 한 번 이동한다.
  이동 전 Controller 목록의 너비·높이를 사용하며 Zone보다 큰 소스·소수 크기도 축소하지 않는다. 수치 입력칸의 미적용 초안을 가져오지 않는다.
- Contents를 버튼에 드롭하면 대상 Zone 중앙에 원본 크기로 추가한다. 원본 크기 미제공 시 기존 크기 입력 안내를 따른다.
- 기존 사용권·권한·설정 버전·대상 revision 검증을 그대로 사용한다. 오래된 항목/취소/사용권 없는 드롭은 전송하지 않는다.
- 실제 WPF 버튼 Click/DragOver/Drop, 캔버스 마우스 경로·합성 TouchDevice를 가짜 Controller/격리 HTTPS 호스트로 검증한다.
  물리 마우스·터치패널·실제 Controller 검증과 구분한다. 근거는 HIPERWALL_VALIDATION.md에 기록한다.

### Hiperwall 드래그·터치 후속 수정 (2026-09-14)

- 인스턴스 응답의 Object zone이 없을 때 사용자가 선택한 유효 Zone을 지우던 문제를 재현·수정했다.
  대응하는 응답 Zone이 있으면 우선 사용하고, 없으면 기존 명시적 선택을 유지한다. Zone을 임의 추론하지 않으며,
  선택이 없으면 이동·크기 조절이 막힌 이유와 Zone 선택 방법을 표시한다.
- 마우스/터치 모두 항목 선택과 바인딩 갱신을 마친 후 입력을 캡처한다. 터치 크기 핸들 판정 영역은 44 DIP이며,
  TouchUp/MouseUp의 최종 위치를 반영한다. 터치에서 파생된 마우스 이벤트가 터치 이동을 중복 처리하지 않게 한다.
- 항목/Zone 변경·캡처 상실·사용권 상실·두 번째 터치는 미전송 드래그를 취소한다.
  한 손가락으로 이동하거나 오른쪽 아래 핸들로 크기를 조절한다. 두 손가락 핀치 크기 조절은 제공하지 않는다.
- WPF 검증은 실제 뷰/바인딩, 합성 TouchDevice의 Down/Move/Up 및 캡처,
  마우스 입력의 선택/편집 경로, 확대 좌표·비율 유지·최종 위치·명령 1회 전송·취소를 확인한다.
  물리 마우스·실물 터치패널·실제 Controller는 미검증이며 가짜 Controller와 격리 HTTPS 호스트만 사용한다.
- 점검 당시 Current는 9월 10일 조회 전용 빌드였다. 최신 앱/호스트 반영 여부는 publish-result.json으로 확인한다.

### Hiperwall 연결·읽기 전용 조회 구현 (2026-09-09)

현재 단계는 단일 활성 Controller 설정, None/Token 인증, 읽기 전용 연결 테스트·목록 조회다.
Core 계약과 Application 권한·수명 로직, Infrastructure HTTP/XML·DPAPI 어댑터를 기존 프로젝트에 추가했다.
WPF는 기존 별도 HTTPS ControlHost API로만 접근하며 가상 조명·작업·교대 구조를 유지한다.
.NET SDK 10.0.400, 런타임 10.0.11과 기존 중앙 패키지·잠금을 유지하고 의존성을 추가하지 않았다.

- 관리자+현재 사용권+설정 버전으로 기존 SQLite에 연결 설정을 저장한다. 원문 토큰은 호스트 DPAPI에 격리한다.
  같은 대상·사용자에서만 토큰 재사용이 가능하며 설정/상태/감사 API는 비밀과 보호 저장 참조를 반환하지 않는다.
- GET /hello와 POST /xmlcommand의 기본 action list/walls만 지원한다.
  상세 공식 명세는 미확인이다. [프로토콜 근거](HIPERWALL_PROTOCOL.md)에 공개 공식 자료·참고 코드·실제 접속 시도·미확인 항목을 분리했다.
- Contents는 Objects/Object의 기본 필드, Zone은 walls 요청이 Zones/Zone을 반환한 경우의 실제 필드를 표시한다.
  ID 없는 항목은 이름으로 확정하지 않는다. 비어 있지 않은 Wall 상세 목록은 필드·식별자 명세가 없어 미지원이다.
  별도 프로필·매핑에서 가짜 Wall/Zone/Contents를 생성하지 않는다.
- Hiperwall 전용 조회 탭과 관리자 설정 영역을 추가했다. 설정 없음, 확인 전/확인 중, 성공, 인증 실패,
  시간 초과, 연결 실패, API·형식 미지원을 구분한다. 실패 때 목록은 비우고 성공 시각은 별도 표시한다.
- 같은 세션의 중복 조회 차단, 요청 순서·설정 버전 재검사, 취소·제한시간, 로그아웃·창 종료 정리를 구현했다.
  호스트 상태만 조회하는 작업은 Controller 요청을 자동 반복하지 않는다. 읽기는 모든 활성 앱 계정에 허용하는 기존 정책을 따른다.
- 한국어 설정 변경·명시적 연결 테스트 감사만 기록하며 반복 조회는 감사 이벤트를 생성하지 않는다.
- XML DTD/외부 자원·리다이렉트를 차단하고 응답 크기·깊이·항목 수를 제한한다.
- 제공받은 http://127.0.0.1:8000에 /hello를 한 번 시도했으나 연결 실패했다.
  실제 버전·인증 성공·목록은 확인하지 못했다. 실제 Controller 호환성은 미검증이다.
- 콘텐츠 표시 변경, Crypto, Enhanced List, 전체 Semantic·카메라·영상·실장비 드라이버는 추가하지 않았다.
  이전 단계표의 Hiperwall 편집·표시 전체 완료로 간주하지 않는다.

- 최초 자체 인증서 유효기간은 2년이며 지문을 통해 현장에서 접속 대상을 확인한다.

### 첫 구현의 확정 완료 범위

여러 PC의 가상 장비 운영으로 다음 흐름을 끝까지 검증한다. 아래는 완료 목표다. 실제 구현 및 로컬/현장 검증 구분은 이 절의 첫 구현 현황을 따른다.

1. 지정한 로컬 데이터 폴더로 별도 호스트 EXE를 실행하고 앱 자체 계정으로 접속한다. 가상 장비를 등록해 역할을 배정한다.
2. 서로 다른 두 PC에서 앱을 실행한다. A가 사용 시작하면 A만 신규 제어하고 B는 조회한다. 동시에 사용 시작을 요청해도 한 세션만 획득한다.
3. A가 일반 명령과 시나리오를 실행한다. 실행 snapshot, 장비 예약, 시나리오 중단 후 수동 전환을 확인한다.
4. 별도 실행에서 A가 미완료 접수 작업을 남긴 채 사용 종료한다. 작업·원 요청자·예약이 유지되고 호스트는 정상 실행을 이어간다.
5. B가 사용 시작해 이전 사용자 작업 표시와 진행 상태를 확인한다. 유지할 작업은 그대로 두고 선택한 작업을 취소한다. 취소와 전송의 경합, 이미 전송한 결과, 시나리오 충돌 정책을 구분한다.
6. 모든 운영자 UI를 종료해도 호스트 EXE와 접수 작업이 유지되는지 확인한다. UI 재시작 후 설정과 호스트 작업 현황을 다시 읽는다. 별도 호스트 재시작은 동일한 지정 폴더에서 작업 기록을 복구하고 불확실한 명령을 중복 전송하지 않는다.
7. 연결 이상을 주입해 이전 세션 신규 명령 차단·진행 작업 확인·관리자 복구 인계·다음 운영자 사용 시작을 확인한다.

한 PC의 앱 두 개로 수행한 검증은 로컬 예비 검증으로만 기록한다. 여러 PC 완료 판정은 실제 서로 다른 두 PC 간 통신을 확인한 뒤 내린다.
초기 가상 검증은 Windows 11 25H2 Pro·Enterprise / x64 지원 범위를 기준으로 진행한다. 가상 검증을 실제 장비·영상 검증으로 간주하지 않는다. .NET 10을 사용하며 SDK 10.0.400 설치를 확인했다. 설치 확인은 앱 빌드·실행 검증을 뜻하지 않는다.
